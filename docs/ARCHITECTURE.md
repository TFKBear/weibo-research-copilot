# 架构文档 · 博研助手（Weibo Research Copilot）

版本：0.1.0（第 1 步交付）
适用范围：技术验证阶段。文中「待验证」标记的条目**尚未在真实微博环境确认**，
其验证方式见 §8。

---

## 1. 定位与技术基线

产品服务于社科类本科生与研究生的**可复现研究流程**，不是舆情监测 SaaS。
这个定位直接决定了三件事：

| 商业舆情的默认做法 | 本工具的做法 | 原因 |
| --- | --- | --- |
| 一键清洗到最干净 | 清洗强度可选，每步可见可关 | 水军话术、情绪化表达在社科研究中本身是研究对象 |
| 输出结论与图表 | 输出结论 **+ 方法卡片 + 清洗报告 + 研究日志** | 论文必须交代结果是怎么来的 |
| 追求吞吐与并发 | 主动限速、串行、设请求硬上限 | 研究场景量级小；高频请求既危险也不必要 |

**技术基线**：Python 3.11+ / FastAPI（后续）/ Playwright / SQLite / HTML+JS 轻前端。
校验用 Python 3.13.1 + Playwright 1.64.1 实测通过。

分层原则：**纯函数留在里层，副作用留在外层。**
解析、时间处理、清洗判定、匿名化、分布统计全部是不依赖网络与磁盘的纯函数，
因而可以被 fixture 完整覆盖；网络、浏览器、磁盘只出现在边界上。

## 3. 三条产品原则如何落到代码

### 3.1 可追溯 → 四份自动产物

| 产物 | 位置 | 作用 |
| --- | --- | --- |
| 研究日志（事件级） | `data/logs/research_log.jsonl` | 每次请求、翻页、停止原因、参数全记录 |
| 研究日志（可读） | 导出目录 `research_log.md` | 可直接改写进论文附录 |
| 方法说明草稿 | 导出目录 `method_note.md` | 采集 + 清洗 + 局限的初稿 |
| 校验和清单 | 导出目录 `manifest.json` | 每个文件的 SHA-256 + 声明记录 |

此外每个数据行都带来源信息：
`created_at_raw`（平台原文）、`created_at_precision`（时间精度）、
`clean_tier` / `pipeline_version`（清洗决策版本）。

### 3.2 可解释清洗 → 步骤表 + 影响报告

清洗不是 `clean(text)` 函数，而是一张**有序步骤表**：

```python
STEPS = [dedupe_exact, drop_empty, drop_pure_emoji, drop_pure_link, drop_pure_mention]
```

每个步骤：有名字、有中文说明、单独计数、可单独关闭（`enabled_steps`）、
被移除的行可按 `cid` 恢复（`CleaningResult.restore`）。

影响报告强制输出三项内容（缺一不可）：各步骤移除量与占比、
被移除样本的随机 20 条（固定随机种子，可复现）、清洗前后的长度与粉丝数分布对比。

**为什么分布对比必须做成默认项**：如果清洗把「低粉丝新用户」整批删掉，
那么之后任何关于「公众意见」的结论都只代表老用户的声音。
这个偏差必须在清洗报告里就暴露，而不是等审稿人质疑。

### 3.3 伦理内嵌 → 匿名化在导出，不在入库

见 §4 ADR-3、ADR-4。这一条是本产品与"爬虫 + 几个图表"最本质的分野之一。

## 4. 关键设计决策

### ADR-1 登录态用 `storage_state` 复用，不实现账密登录
- **选项**：a) 用户输入账号密码，程序自动登录；b) 弹窗扫码，保存浏览器上下文；c) 用户粘贴 Cookie。
- **决定**：b 为主，c 为降级，明确不做 a。
- **理由**：a 意味着把用户密码接进工具，风险与伦理都不划算，且极易触发风控与二次验证。
  b 与用户的日常使用行为一致，风控风险最低，且 `storage_state` 可整体复用。
- **代价**：登录态有时效（通常数天），需要周期性重新扫码；工具必须能给出清晰的过期提示。

### ADR-2 传输以 `APIRequestContext` 为主，页面内 `fetch` 为备
- **选项**：a) `requests/httpx` 直连 + 手动搬 Cookie；b) Playwright 页面内 `fetch`；c) Playwright 的 `context.request`。
- **决定**：c 默认，b 可切换（`WRC_FETCH_MODE=page`）。
- **理由**：a 需要自己维护请求头与 Cookie 同步，且 TLS 指纹与浏览器不同，风控更易命中；
  b 指纹最真实，但依赖页面来源（跨域失败）且需要常驻页面；
  c 自动继承上下文 Cookie 与 UA，不受 CORS 限制，是稳定性与真实性的平衡点。
- **代价**：c 的 TLS 指纹仍是 Playwright 的 HTTP 栈而非浏览器本身。若实测被拦，切到 b。

### ADR-3 匿名化在导出层，不在入库层
- **理由**：入库即抹掉身份，P1 的「用户社群聚类」无法把同一用户的多条评论聚合，
  用户级分析路径被提前焊死。正确做法是**入库保留、导出脱敏**。
- **兜底**：导出前强制跑 `assert_no_identifiers()`，宁可导出失败也不输出带 ID 的数据。

### ADR-4 伪 ID 用 HMAC(本地盐, user_id)，不用自增序号
- **理由**：自增序号在多表 join 时易错，且跨两次导出不稳定；
  HMAC 保证同一用户 ID 稳定、跨账号无法反查、盐泄漏前不可逆。
- **代价**：盐文件（`data/keys/pseudo_salt.bin`）必须备份，否则历史导出无法与新导出关联。

### ADR-5 存储用 SQLite，不上 PostgreSQL / Elasticsearch
- **理由**：研究级数据量（单次 10³–10⁵ 行）SQLite 完全够用；零部署，学生换电脑拷一个文件就走；
  WAL 模式支持读写并发。清洗层与原始层同库不同表，重跑清洗不需要迁移。
- **触发升级的条件**：多用户并发写、或单表 > 10⁷ 行。目前不需要。

### ADR-6 清洗做成可组合步骤，而不是单一函数
- 见 §3.2。核心收益是「误杀可回退」和「报告可解释」，这两点在单一函数结构里做不到。

### ADR-7 所有用户可见错误必须是 `WrcError`
- 统一转译为「发生了什么 + 你可以做什么」。原始异常只进日志。
- 例子：浏览器未安装 → 直接告诉学生 `python -m playwright install chromium`；
  被限流 432 → 说明已自动暂停多少秒，并给出三个可选动作。
- **代价**：新增错误路径时要记得包装，否则会退化成一个"未预期错误"。

### ADR-8 「按热度 / 按时间」明确标注为本地重排
- **问题**：移动端检索接口返回的是相关度排序，站内的「热门/实时」排序参数是否可用尚未验证。
- **决定**：`order` 支持 `platform` / `engagement` / `time`，后两者是**本地对候选集重排**，
  在研究日志与 UI 文案中一律标注「本地重排，不等于平台排序」。
- **理由**：如果把本地按互动量排序说成"平台热门"，研究者会在论文里写错方法。
  宁可功能弱一点，也不能描述错。

### ADR-9 评论抽样偏差显式记录
- 评论来自 `comments/hotflow`（热门评论流），天然偏向高互动评论。
- 每篇帖子的采集结果都记录 `stopped_reason`（目标量达成 / 平台无更多 / cursor 停滞 / 分页上限 / 预算耗尽）
  与 `sample_bias`，并写入方法说明的「已知局限」。

### ADR-10 时间必须带精度标签
- 微博检索结果混用「刚刚 / 3分钟前 / 今天 10:23 / 05-12 / 2024-05-12」。
- 把只精确到「日」的时间补成 `00:00:00` 是隐性造假，会污染时间序列分析。
- 因此保留 `created_at_raw` + `created_at_precision`（second/minute/day/unknown），
  由研究者在分析阶段自行决定如何加权或剔除。

### ADR-11 离线 MockFetcher 是一等公民
- 采集链路的边界（cursor 停滞、目标量不足、预算耗尽、432 重试）在真实数据上很难稳定复现。
- 用 `MockFetcher` + 确定性场景把整条管线变成可测、可演示、不依赖网络的代码。
- 收益：接口波动时我们能判断"是微博变了"还是"我们的代码坏了"。

### ADR-12 导出 CSV 用 UTF-8 BOM
- 目标用户用 Excel 打开数据；不带 BOM 的中文 CSV 在 Excel 里是乱码。
- 一个字节的差异，决定学生第一眼看数据时是"能用"还是"坏了"。

### ADR-13 评论来源建模成「后端」，而不是硬编码一个接口
- **背景**：微博同时存在移动端 `comments/hotflow` 与网页端
  `ajax/statuses/buildComments` 两套评论接口，参数、Referer、响应结构都不同，
  且各自独立变化。
- **决定**：`wrc/weibo/comment_backends.py` 定义后端，采集时 `auto` 逐个尝试，
  成功者写入研究日志。
- **理由**：一个后端返回空时，工具需要能换一个继续，而不是把空当结论；
  同时"数据来自哪个后端"本身就是抽样方法的一部分，必须可回查。
- **附带收益**：网页端的 `flow` 参数是唯一确认能表达「按热度 / 按时间」的排序开关，
  这让评论排序成为一个可交代的抽样决策，而不是"平台给什么拿什么"。

### ADR-14 「接口返回空」与「本来就没有」必须区分开
- **背景**：第 1 步实机测试中，一个显示 679 条评论的帖子，评论接口返回
  `ok=1` 但 `data` 为空。旧代码把它归为 `stopped_reason=no_more_from_platform`，
  于是流程继续在**空样本**上跑清洗与情感分析，日志里还看不出异常。
- **决定**：引入 `CommentSourceEmpty`。当 `expected_total > 0` 而所有后端都返回空时，
  直接抛错并给出诊断命令；只有 `expected_total == 0` 才允许空结果通过。
- **理由**：这是本工具最危险的一类失败——它不报错、不中断、产出一份看起来
  正常的空数据集。对研究工具来说，**静默的空结果比明确的报错危险得多**。
- **代价**：偶尔会为"这个帖子确实刚被删光评论"多报一次错，需要人工确认。
  这个方向的误报是可接受的。

### 被否决的方案
| 方案 | 否决原因 |
| --- | --- |
| Selenium | 反检测能力弱、API 笨重、同步模型与 FastAPI 不搭 |
| 纯 requests + 代理池 | 登录态难长期维持；代理池本身是滥用边界的开始 |
| 打码平台 / 验证码识别 | 明确的越界行为，与学术工具的定位冲突，不做 |
| 并发抓取 | 研究场景不需要吞吐；并发显著抬高风控命中率 |
| MongoDB | 研究数据是表格型，SQLite 更利于学生自查与二次分析 |

## 5. 采集链路

```
登录态检查 (/api/config)
    → tag 检索 (container/getIndex, page=1..N)
        → 帖子预览（时间 / 互动量 / 评论数 / 摘要）
            → 用户显式选帖（--select / 交互输入；非交互环境必须给参数）
                → 逐帖评论采集 (comments/hotflow, max_id 递推)
                    → [可选] 二级评论 (comments/hotFlowChild)
                        → 落库 raw_*
```

**翻页的正确做法**（已写入代码与测试）：
- `max_id` 必须原样回传上一页响应中的值；
- `max_id_type` 必须与上一页响应一致，否则会拿到重复页；
- **必须检测 cursor 是否推进**。接口退化时会重复返回同一个 `max_id`，
  不做检测就会「无限翻页 + 全是重复数据 + 白白放大风控风险」。
  检测到停滞即停止，并把 `cursor_stalled` 记入日志。
- 二级评论默认关闭：数据量呈数量级增长，且每多抓一条就多一次风控暴露。
  开启时只对「有跟评的一级评论」抓前若干条，并受预算约束。

**频率纪律**（`wrc/weibo/ratelimit.py`）：
- 请求间随机延迟 1.5–3.0 秒（均匀抖动，避免固定节律）；
- 命中限流按 60s → 120s → 240s 退避，±15% 抖动，封顶 600 秒；
- 单次采集出站请求硬上限（默认 120，含重试），到 80% 主动提示用户；
- 全体串行，不并发。

## 6. 数据模型

```
collection_runs   一次采集的元信息（tag / 排序 / 全部参数 / 状态）
      │
      ├── raw_posts       帖子的原始字段（含 user_id，供内部关联）
      ├── raw_comments    评论的原始字段（含 user_id / followers_count）
      ├── clean_comments  清洗决策（kept / drop_reasons / clean_tier / pipeline_version）
      └── research_events 事件流（与 JSONL 日志互为备份）
```

- `raw_*` 与 `clean_*` 通过 `(run_id, cid)` 关联，**清洗随时可从原始层重跑**。
- 原始层保留 `user_id` 是刻意设计（见 ADR-3），导出层才会脱掉。
- 三层导出：原始层 / 分析层 /（第 2 步起）报告层。

**导出字段白名单**：`anonymize_comment()` 只输出白名单字段。
即使以后底层表新增字段（如 `ip_region`、`device`），也不会意外泄漏——
这一点有专门的测试覆盖。

## 7. 错误处理与降级

`WrcError` 的九种语义分类：
`AUTH_REQUIRED` / `RATE_LIMITED` / `RISK_BLOCKED` / `NETWORK` / `API` / `PARSE` / `BUDGET` / `CONFIG` / `CONSENT`。

响应语义翻译集中在 `fetching.interpret_response()`，一张表决定一切：

| HTTP / 内容 | 分类 | 可重试 | 用户可见文案要点 |
| --- | --- | --- | --- |
| 418 / 429 / 432 / 503 | RATE_LIMITED | 是 | 已自动暂停 N 秒；可缩小范围或换时段 |
| 403 / 412 / 返回 HTML 验证页 | RISK_BLOCKED | 否 | 需手动完成验证；调大延迟 |
| 401 / 重定向到 passport | AUTH_REQUIRED | 否 | 登录态过期；重新扫码 |
| 5xx | API | 是 | 平台侧暂时不可用 |
| 响应是 HTML 登录页 | AUTH_REQUIRED | 否 | 同上 |
| JSON 结构不符 | PARSE | 否 | 接口可能已调整；跑 03_probe |
| 预算耗尽 | BUDGET | 否 | 已保留已采数据 |

**预算耗尽的处理值得单独说明**：不静默失败、不丢进度。
脚本会保留已采数据，继续走清洗与导出，并在日志中写明 `status=partial`。

## 8. 尚未验证的假设（重要）

以下条目在开发时**无法在不接触真实环境的情况下确认**。它们已做成可执行的探测项
（`spikes/03_probe.py`）。第 1 步交付时已在**未登录基线**下跑过一轮，结果见 §8.1；
带 ✅ 的条目已经有实测结论，其余需要一位真实用户登录后重跑探测才能确定。

| # | 假设 | 若不成立的后果 | 现状 |
| --- | --- | --- | --- |
| 1 | 扫码登录后 `storage_state` 可稳定复用 | P0 整条链路不成立，须改走 Cookie 路径或换方案 | ✅ 实测可用（30 个 Cookie，含 `SUB`/`SUBP`） |
| 2 | `m.weibo.cn` 检索接口返回 `card_group`/`mblog` 结构 | 检索解析失效 | ✅ 实测可用（一次拿到 20 篇帖子） |
| 3 | 检索第 2 页与第 1 页不重叠 | 只能拿到首屏，样本代表性下降 | ⏳ 待确认（上一轮登录后未跑完） |
| 4 | `containerid` 的 `type` 参数能切换检索 Tab | 「按热度」只能是本地重排（当前已如实标注） | ⏳ 待确认 |
| 5 | 桌面页 `Refer=hot` 仍对应热门排序 | 同上 | ❌ **桌面路径已实测不可用**（见 §8.1） |
| 6 | 评论 `max_id` 递推稳定 | 单帖只能拿到首屏 | ✅ 实测可用（50 条 / 6 页），但**响应结构已变**：`data` 是数组、游标在顶层、`max_id_type` 消失 |
| 7 | 二级评论接口在无跟评时返回空结构 | 开启二级采集时报错 | ⏳ 待确认 |
| 8 | 桌面 UA 不影响 m 站接口 | 需切移动端 UA | ✅ 未登录与已登录请求均被正常受理 |
| 9 | 默认延迟（1.5–3s）+ 120 次上限不触发 432 | 需下调频率或上限 | ⏳ 需持续观察 |
| 10 | `s.weibo.com` 桌面检索页可解析 `$render_data` | 降级路径不可用（不影响主链路） | ❌ 实测重定向到访客关口 / 超时 |
| 11 | 评论接口能在 `auto` 模式下自动找到可用后端 | 需人工指定 `--comment-backend` | ✅ 实测有效（移动端优先，四后端均可用） |

### 8.1 第 1 步实测记录（未登录基线）

环境：Windows 11 / Python 3.13.1 / Playwright 1.64.1 / 系统 Chrome 引擎（回退）。

| 请求 | 结果 | 结论 |
| --- | --- | --- |
| `GET m.weibo.cn/api/config` | 200，`{"ok":1,"data":{"login":false}}`，并下发访客 Cookie `MLOGIN / WEIBOCN_FROM / XSRF-TOKEN / _T_WM` | **传输链路可用**：APIRequestContext + 自定义 Header 能正常拿到 m 站 JSON，排除了"完全连不上"的风险 |
| `GET m.weibo.cn/api/container/getIndex?...page_type=searchall` | `{"ok":-100}` | **检索必须登录**，与需求文档的判断一致：登录态是整条链路的硬前提 |
| `GET s.weibo.com/weibo?q=...&Refer=g` | 首次被重定向到 `passport.weibo.com/visitor/visitor?...`；重试 20s 超时 | **桌面站点不能作为降级路径**，已从"备用采集通道"降级为"仅探测用" |
| `python -m playwright install chromium` | 下载 79MB 后停滞；换 npmmirror 镜像同样停滞 | 已实现**系统 Chrome / Edge 自动回退**（`system_browser_fallback`），实测可正常驱动 |

由此产生的三条设计修正（已写入代码）：

1. **删除"桌面页作为降级采集通道"的定位**，只保留探测用途；主链路必须走 `m.weibo.cn` + 登录态。
2. **失败信息不要贴 Playwright 的完整请求日志**（几百行的 header 清单），只取首行进用户可见区。
3. **浏览器引擎自动回退**：内置 Chromium 不可用时依次尝试本机 Chrome、Edge，
   并把实际使用的引擎写进研究日志（引擎属于方法的一部分）。

**处理原则**：凡是未验证的，代码注释、文档与用户可见文案里都标为「待验证」，
不把猜测写成事实。这也是本产品对研究者的基本尊重。

### 8.2 第 2 轮实测（登录后，用户真实环境）

用户完成扫码登录后在自己的机器上跑通了前半段，结果如下：

| 步骤 | 结果 | 结论 |
| --- | --- | --- |
| 扫码登录 → `storage_state` | 30 个 Cookie，含 `SUB` / `SUBP` / `SSOLoginState` / `WBPSESS` | **假设 1 成立**：浏览器登录态复用可行 |
| tag 检索 `#小米SU7#` | 一次拿到 20 篇帖子，时间/互动/评论数齐全 | **假设 2 成立**：检索解析正确 |
| 评论采集（679 条评论的帖子） | 移动端 hotflow 返回 `ok=1` 但 0 条数据，被旧代码记为 `no_more_from_platform` | **故障**：空数据被当成空结果，见 ADR-14 |
| `03_probe.py` | 探测记录落盘时崩在 `TypeError: Object of type WeiboPost is not JSON serializable` | 探测脚本自身的序列化 bug（slots dataclass 没有 `__dict__`） |

由此产生四项修复：

1. **`CommentSourceEmpty`**：`expected_total > 0` 且所有后端返回空 → 直接报错并给出诊断命令。
2. **评论后端抽象**（ADR-13）：`mobile_hotflow` / `web_build_comments` / `mobile_hotflow_reload`
   三个后端，`auto` 模式逐个尝试，成功者写入研究日志。
3. **评论请求的 Referer 改为帖子详情页**：从站点首页作为 Referer 打评论接口，
   在风控看来与实际浏览行为不一致，这是最可能的空数据原因之一。
4. **探测脚本序列化修复**：`_jsonable` 显式支持 `dataclass(slots=True)`。

新增诊断工具 `spikes/04_probe_comments.py`：把每个候选后端都请求一次，
打印 `ok` / `msg` / `data` 真实结构 / 首条评论字段名，并把原始响应落盘。
这是目前唯一能在不猜测的前提下确定"评论到底该从哪拿"的方法。

**诊断结论：根因是解析器跟不上接口结构变化，不是风控，也不是 Referer。**

移动端 hotflow 的真实响应已经变成：

```json
{"ok": 1, "data": [ {...} ], "max": 200, "max_id": 13886361396130283, "total_number": 679}
```

而旧解析器要求 `data` 是对象、评论在 `data.data` 里 —— 于是 `data` 是数组时
直接返回空页，连 `ok` 都没检查。四个后端其实一直都能用。

同一次诊断还暴露了一个更隐蔽的字段错误：评论者的
`user.followers_count` 返回的是**字符串 `"2733.7万"`**，
旧的"去除非数字"处理得到 `27337`，比真实值小 1000 倍。
这个错误不会让任何测试失败，却会让 B2 的"清洗前后粉丝数分布对比"失去意义。
已在 `_to_int` 中处理 `万/亿/千/w/k` 与千分位，并有参数化测试锁定。

修复后真实链路验证：`#小米SU7#` 下一个显示 679 条评论的帖子，
采到 50 条、翻 6 页、`reached_target`，清洗与匿名化导出全部正常。

## 9. 风险、合规与伦理边界

### 9.1 平台侧
- 自动化采集可能与微博用户协议存在张力。工具的设计取向是**尽量降低危害**：
  使用研究者自己的账号、串行低频、设硬性请求上限、只读公开内容。
- **不做的三件事**：不绕过验证码、不采集非公开内容（私信、粉丝可见）、不规避付费限制。
- 出现验证或 432 时工具**停下来提示用户**，不做自动绕过。这是刻意的产品边界。

### 9.2 研究者侧
- 导出前强制阅读并确认《数据使用声明》（6 条），确认动作记入研究日志。
- 导出数据不含 `user_id` / `screen_name` / `profile_url` / `location` 原始值。
- 交叉表 k-匿名抑制（n < 5 不展示）已作为可复用原语提供（`suppress_small_groups`）。

### 9.3 已知残余风险（须在使用说明中披露）
1. 评论文本本身可能包含自我披露信息（职业、单位、住址），**匿名化字段不等于匿名化文本**。
   大规模引用原文仍有再识别风险，需研究者自行处理。
2. 伪 ID 在同一盐下跨数据集稳定；若两份数据集同时公开，可做跨集关联。
   敏感研究中应每次导出使用新盐。
3. 评论来源是热门评论流，天然偏向高互动内容；结论不能外推到"该帖全部评论"。
4. 检索结果的抽样不是概率抽样，无法直接计算抽样误差。

## 12. 分析层现状（P1–P3 落地后）

第 1 步只规划到导出层。P1–P3 完成后的分析层结构如下，作为对 §2 总览的补充：

```
                    ┌──────────────────────────────────────────┐
                    │  service.py（编排：跑分析 + 落库一件事）    │
                    └───┬───────┬───────┬───────┬───────┬──────┘
                        │       │       │       │       │
              ┌─────────▼─┐ ┌───▼────┐ ┌▼──────┐ ┌▼──────┐ ┌▼────────┐
              │ sentiment │ │cluster │ │community│ │timeseries│ │ replies │
              │  LLM+本地 │ │句向量   │ │行为特征 │ │时间聚合  │ │parent_cid│
              └─────────┬─┘ └───┬────┘ └────┬───┘ └────┬────┘ └────┬────┘
                        └───────┴───────────┴──────────┴───────────┘
                                          │
                              ┌───────────▼────────────┐
                              │ report.py（拼装七节报告）│
                              │ + method_card + crosstab│
                              │ + docx_export           │
                              └───────────┬────────────┘
                                          │
                              ┌───────────▼────────────┐
                              │ charts.py（每会话 7 类图）│
                              └────────────────────────┘
                                          │
                    compare.py（跨话题对比，读多个会话的画像）
                    reproducibility.py（可复现性附录：等级 + 指纹 + 校验和）
```

三个设计约定，P1 起一直保持：

1. **凡有产出必须落库**。分析结果进 `analysis_runs` / `analysis_comments`，
   报告可随时从数据库重建，不必重跑 LLM（省钱且结果可复现）。
2. **报告层只排版，不取数**。`report.py` 只接收已经算好的结果对象；
   取数与合并逻辑在 `service.py`（`_merge_analysis` 等）。
3. **不调模型的模块总是跑**。时间演变、回复结构、交叉表都是对已有结果的
   重新组织，没有额外成本，所以每次生成报告都会重算，比读旧摘要更可靠。

### 分析层的"逆向能力"：每个模块都必须会拒绝

| 模块 | 什么情况下它会明确拒绝给结论 |
| --- | --- |
| 情感 | LLM 不可用 → 只出本地通道并标注为粗筛参照 |
| 话语聚类 | 轮廓系数 < 0.25 → 告警"标签不宜写进论文" |
| 用户社群 | 某簇 < 3 人 → 告警"只能当个案看，不能当群体结论" |
| 时间演变 | 前后两段任一侧 < 30 条 → "不做趋势判断" |
| 回复结构 | 无 level≥2 记录 → "没采到 ≠ 没人回复" |
| 交叉表 | 分组样本 < 5 → 整行或整格抑制 |
| 跨话题对比 | 参数不一致 / mock 混入 → 判为不可比并说明原因 |

这张表是产品原则第二条（"可解释的清洗优于最大程度的去噪"）在分析层的对应物：
**宁可少给一个结论，也不给一个站不住的结论。**
