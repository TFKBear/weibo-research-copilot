# 020 · 一次真实运行暴露的四个问题（已修）

日期：2026-10-26　状态：已实施　测试：`tests/test_export_refresh.py`、`tests/test_deliverables.py`

会话 `20261026T195346-6d31`（研究者本人操作，2026-10-26 19:53）是第一次
"别人按自己的理解跑一遍"的真实数据。结果目录和日志看下来，有四个问题。

| 项 | 实测 |

## 问题一：导出的研究日志是空表（真 bug）

`research_log.md` 只有 141 字节：表头 + 一行都没。

原因：导出发生在**另一个进程**里，`write_research_log()` 新建的 `ResearchLog`
内存里没有任何事件，也不去读磁盘上的 JSONL——于是把 133 条真实事件丢掉了。
而这份文件正是"可复现性"最直接的证据，空表等于没有过程记录。

修：`write_markdown()` 在内存为空时先从磁盘读回该会话的事件（并过滤 run_id）。
修复后该会话重生成，`research_log.md` 从 141 字节变成 39,757 字节 / 133 行事件。

## 问题二：方法说明里「实际选中帖子数」是 `-`

这是占位符一直没被填过。真实运行里"选中 20 篇"与"成功 11 篇"差 45%，
恰恰是最该写进方法段的一行——不写，读者会以为 20 篇都采到了。

修：导出时按帖子表与评论表算 `attempted / succeeded`，写成
`20 篇（成功 11 篇，跳过 9 篇）`。

## 问题三：附录完全不提进样率

附录写了"运行状态 partial"，但没说为什么 partial。
新增一行「进样率：20 篇中成功 11 篇，跳过 9 篇（接口返回暂无数据/帖子不可见）」。

## 问题四：时间窗的 ISO 字符串读不回来

参数里存的是 `2026-01-01T00:00:00+08:00`，而 `parse_window_time()`
只认界面上那种"年-月-日 时:分"的写法，遇到 ISO 直接抛
`ValueError: 看不懂这个时间`。

后果很隐蔽：只要想**事后重生成**任何产物（附录、方法说明、日志）就会崩，
也就是"导出的东西只能一次成型，改不了"。修：先尝试 ISO（含 `T` 时），
其它写法仍走原分支，`end_of_day` 语义不受影响。

## 顺带修的两处

- `write_method_note()` 假设清洗步骤一定带 `description`，
  而 `cleaning_facts()` 返回的步骤只有 label/removed/share → `KeyError`。
  现在缺 description 时只写"移除 N 条（x%）"。
- 附录参数表里空 dict 渲染成空白单元格，看不出"没设"还是"读丢了" → 现在写 `无`。

## 新增：`tools/refresh_exports.py`

这次四个问题里，有三个只影响"文字类"产物。让研究者为了修一句话重采一遍，
是不可接受的。所以加了一个只重写文字的入口：

```bash
python tools/refresh_exports.py --run <id>            # 重写 research_log.md / method_note.md / appendix.md
python tools/refresh_exports.py --run <id> --dry-run  # 只看将要写入的口径
```

不动 `raw/` 与 `analysis/` 下的数据文件。为了两边口径一致，
`method_note` 的参数表抽成了 `build_method_params()`，导出与重生成共用同一份。

## 交付物自检也加了一条

`tools/check_deliverables.py` 现在会检查 `research_log.md` 是否有事件行——
空表直接 ERROR。这个 bug 能活到今天，就是因为没有任何检查盯着它。

另给 `tools/check.py` 加了 `--skip-deliverables`：交付物自检反映的是**本机数据状态**
（比如最近一次采集没跑分析），不该和代码质量混在一句话里。

## 仍未解决（需要人）

这次运行**没有跑分析**，所以没有报告、图表与情感/立场标签。
界面上的「开始采集并分析」只做采集→清洗→导出；分析要再点

是否要把两步合成一次点击，需要研究者判断（跑分析要花模型调用与时间）。
