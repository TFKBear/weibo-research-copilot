### 最严重的那一条

`stopped_reason=no_more_from_platform` 的意思是"平台说没有更多评论了"。
但该帖显示 **679 条评论**。也就是说：

> 一个明确存在的故障，被工具翻译成了"这个帖子没有评论"，
> 然后流程安静地继续往下走，产出一份**看起来正常的空数据集**。

如果这次不是你在第 1 步就发现了，而是等到后面跑情感分析时才看到"0 条结果"，
排查成本会高一个数量级；如果是别人用这份数据写了论文，那就是学术事故。

**这类"静默的空结果"是研究工具最不能容忍的失败模式**——它不报错、不中断、
不留痕迹。所以这次不是修一个 bug，是改一条原则。

## 2. 改了什么

### 2.1 新增错误类型：`CommentSourceEmpty`

规则变得简单且严格：

- 平台显示该帖有 N 条评论（N > 0），而所有候选后端都返回空 → **抛错**，
  并直接给出诊断命令；
- 平台显示 0 条评论 → 空结果是正确答案，正常返回。

对应 4 项测试，其中一个专门锁死"679 条评论却拿到空"这个场景。

### 2.2 评论来源建模成「后端」

微博同时有移动端 `comments/hotflow` 与网页端 `ajax/statuses/buildComments`
两套评论接口。现在把"从哪拿评论"显式建模：

| 后端 | 特点 |
| --- | --- |
| `mobile_hotflow` | 主流抓取方案，平台热门排序，无排序参数 |
| `web_build_comments` | 网页端接口，**`flow` 参数可控制按热度 / 按时间** |
| `mobile_hotflow_reload` | 同上但带 `is_reload=1`，部分帖子只有带它才返回数据 |

`auto` 模式按顺序尝试，**谁成功谁被写进研究日志**。换后端等于换抽样方式，
这属于方法的一部分，必须可回查。

附带收益：`flow` 是唯一确认能表达「评论按热度 / 按时间」的开关，
这让评论排序成为一个**可交代的抽样决策**，而不是"平台给什么拿什么"。
新增 `--comment-sort hot|time`。

### 2.3 评论请求的 Referer 改为帖子详情页

从站点首页作为 Referer 直接打评论接口，与真实浏览行为（先打开帖子再看评论）
在风控看来是两件事。这是"空数据"最可能的原因之一，已改为
`Referer: https://m.weibo.cn/detail/{mid}`。

### 2.4 修复探测脚本的序列化崩溃

`_jsonable` 用 `hasattr(obj, "__dict__")` 判断对象类型，而 `dataclass(slots=True)`
的实例没有 `__dict__`，于是 `WeiboPost` 一路漏到 `json.dumps`，把整份探测记录炸掉。
现在显式用 `dataclasses.is_dataclass` + `dataclasses.fields` 处理。

**这个 bug 的教训**：诊断工具本身必须比被测系统更可靠。一个会在最后一步崩掉
的诊断脚本，等于在最需要信息的时候把信息弄丢了。

### 2.5 新增 `spikes/04_probe_comments.py`

把每个候选后端都请求一次，打印：
`ok` / `msg` / `data` 的真实结构 / 拿到几条 / **首条评论的字段名**
（字段名决定解析器能不能对上，例如 `like_counts` 还是 `likes_count`）。

原始响应全部落盘到 `data/logs/comments_probe_<时间>/raw_*.json`，
可以直接发出来，不需要靠猜。

## 3. 根因（已用真实响应确认）

诊断脚本跑完后，四个候选后端**全部拿到了数据**。所以问题从来不是风控，
也不是 Referer，而是**解析器跟不上接口结构变化**。

真实响应（`data/logs/comments_probe_*/raw_mobile_hotflow_hot.json`）：

```json
{
  "ok": 1,
  "data": [ { "id": "5308980077529786", "text": "...", "created_at": "Fri Jun 12 13:42:29 +0800 2026",
              "like_count": 1547, "total_number": 93, "floor_number": 4,
              "user": { "id": 1749127163, "followers_count": "2733.7万" } } ],
  "max": 200,
  "max_id": 13886361396130283,
  "total_number": 679
}
```

关键差异：

| 项目 | 旧代码的假设 | 实际情况 |
| --- | --- | --- |
| `data` | 对象，评论在 `data.data` | **数组**，评论直接在 `data` |
| 游标 / 总数 | 在 `data.max_id` / `data.total_number` | 在**顶层** |
| `max_id_type` | 必须回传 | **已不存在** |
| 点赞数 | `like_counts` | **`like_count`**（单数） |
| 评论者的跟评数 | `total_number` | 仍是 `total_number`（与顶层同名字段含义不同，容易混淆） |
| 粉丝数 | 整数 | **字符串 `"2733.7万"`** |
| 单页条数 | 20 | 移动端 **10**、网页端 20 |

旧代码在第 2 行就退出：

```python
if not isinstance(data, dict):
    return CommentPage()      # data 是 list → 直接返回空页，连 ok 都不看
```

### 附带发现的一个更隐蔽的 bug

`_to_int("2733.7万")` 原来是「去掉所有非数字字符」→ `27337`。**比真实值小 1000 倍。**

它不会让任何测试失败，也不会让人看出异常——直到有人盯着
「清洗前粉丝数均值」那一栏觉得奇怪。而粉丝数分布正是 B2 用来判断
「清洗有没有引入系统性偏差」的核心指标。这种量级错误
恰恰是最难被自己发现的一类。

已在 `_to_int` 中处理 `万 / 亿 / 千 / w / k` 与千分位，
并有 9 个参数化测试锁定。

### 我上一轮的推测错在哪

上一轮我判断"最可能的原因是 Referer 不是帖子详情页"。这个判断是**错的**：
真实响应表明 Referer 不是决定因素。Referer 的改动保留了下来（更贴近真实浏览行为，
风险更低），但它是防御性改进，不是修复。把推测写清楚、并在被证伪时明确标注，
本身就是这个产品要求的可追溯性。
