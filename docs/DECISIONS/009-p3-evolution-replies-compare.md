- 阶段：自主推进（P3）
- 状态：三项均已实现；前两项在真实数据上跑通，第三项因只有 1 个真实话题，
  只能验证"不可比时会拒绝比较"这条路径

P3 是交付节奏里最后一个阶段。三项的共同点是：**它们都可能产出看起来很有说服力
但实际站不住的结论**，所以每个模块的第一职责是"什么时候不该下结论"，
第二职责才是算指标。

## 1. 时间演变（`wrc/analyze/timeseries.py`）

### 三个必须先说清楚的前提

1. **采集不是时序完整的**。评论来自「热门评论流」，平台按热度而不是时间返回。
   所以曲线描述的是**已采集样本的时间分布**，不是平台全量舆论的演化轨迹。
   这句话写进了 `render()` 的结尾和报告的方法卡片，不是藏在代码注释里。
2. **时间精度不齐**。检索结果里混着只精确到「日」的时间戳。把这种记录塞进小时桶，
   等于把 00:00 当成"凌晨爆发"——这是隐性造假。所以一旦发现日级精度，
   **强制降级为按日聚合**，并在结果里说明原因。
3. **小时段样本太小**。n<5 的时段占比标为 `—`、图上用空心点、且**不参与趋势判断**。

### 趋势判断刻意保守

只有同时满足「前后两段各 ≥30 条」且「占比变动 ≥10 个百分点」才说"观察到变化"，
否则明确输出"不做趋势判断"。真实数据（46 条 / 3 个时段）上的输出是：

```
趋势判断：前后两段样本量不足（37 条 vs 9 条，各需 ≥30 条），不做趋势判断。
⚠ 评论量高度集中：2026-06-12 一个时段占了 37/46 条。
```

也就是说，**这个模块在现有样本上主动拒绝给结论**。我认为这是正确行为：
一个 46 条样本上的"舆情演化趋势"写进论文，评审一句"样本量"就会毙掉。

### 图上的一个设计细节

评论量用灰柱画在右轴，情感占比用折线画在左轴。只画占比的话，一个只有 1 条评论的
时段会画出"100% 负面"的尖峰，看起来像舆情突变；柱子让人一眼看出那是噪音。

## 2. 二级评论回复结构（`wrc/analyze/replies.py`）

### 现实约束

**二级评论默认不采集**（产品决策 001）。所以这个模块在绝大多数会话上拿到的是空数据。
它因此明确说：

> 本次数据中没有二级评论，无法分析回复结构。
> （本次会话有 46 条评论，但没有任何 level≥2 的记录。这有两种可能：
> ①采集时未开启二级评论；②开启了但该批帖子确实无人回复。
> 评论接口不返回「是否采集了二级评论」的标记，所以工具无法区分这两种情况——
> 请回想采集设置，不要默认「没人回复」。）

写这段花的时间比写指标还多，但它是必要的：**"没采到"和"没有"是两件事**，
合并成一句"无人回复"就是编数据。

### 清洗会打断回复链

父评论被判定为垃圾移除后，它的子评论成了孤儿。本模块把孤儿挂到该帖虚拟根上
并**单独计数**、单独告警。静默重挂会让研究者以为"讨论本来就这么浅"。

### 隐私

节点只带层级与父子引用，`to_dict()` 里连 `cid` 都剥掉了——一张能对应到
"某条评论下连续 20 条回复"的图就接近可识别。小讨论串（节点数 <5）不展示、不列举。

### 四种形态

`单点引爆型`（最大串占回复 ≥50%）/ `多层对话型`（深度 ≥3）/ `多点分散型` /
`仅有根评论`。这是描述性命名，不是对舆论性质的判断。

## 3. 跨话题对比（`wrc/analyze/compare.py`）

### 这是全工具最容易出假结论的功能

"话题 A 评论比 B 多"——如果两次采集的每帖上限不同，这句话就是错的。
工具必须在源头拦住它。所以输出分三段，**可比性判断在前，对比表在后**：

```
可比性判断：**仅绝对量可对比（占比不可比）**

参数差异（这些差异决定了哪些结论能说）
  · 评论后端不同：auto（1 次）；未记录（2 次） —— 不同后端返回的评论集合不同。未记录不等于相同，无法假定一致。
  · 清洗档位不同：light（2 次）；未记录（1 次） —— 档位不同则情感/主题占比不可直接比。未记录不等于相同，无法假定一致。
```

（这是真实数据库里的三个历史会话，参数记录不全，所以两个维度都被判为不可比。）

### 规则

| 判定 | 依据 |
| --- | --- |
| 绝对量可比 | `mode`、`post_limit`、`comments_per_post` 全一致 |
| 占比可比 | `mode`、`clean_tier`、`comment_sort`、`comment_backend`、`include_subcomments` 全一致 |

- **mock 与 live 永不可比**：mock 是内置样例数据，混在一起读者分不出来。
  命令行默认排除 mock，`--all` 才能带上，且会给出强烈告警。
- **未记录 ≠ 相同**：老会话缺参数记录时判为不可比，而不是假设一致。
- 不可比时，表格里对应列显示 `—`；占比不可比时**不出对比图**——
  一张画出来的图比一张表格更容易被当作结论。

### 顺手补采了一个真实话题

原来库里只有 `#小米SU7#` 一个真实话题（另外两个是 mock），跨话题对比无从验证。
所以补采了一次 `#延迟退休#`（2 帖 × 30 条，采集 60 条、清洗保留 58 条、保留率 96.7%），
并跑完情感与聚类（K=2，轮廓系数 0.1562，同样偏低）。

真实输出：

```
可比性判断：**仅占比可对比（绝对量不可比）**

参数差异（这些差异决定了哪些结论能说）
  · 每帖评论上限不同：30（1 次）；50（1 次） —— 上限不同则绝对量不可比

话题                评论数     保留率      正面      中性      负面
#延迟退休#             60     97%     5%     26%     69%
#小米SU7#            50     92%    17%     24%     59%

⚠ 评论量不能直接横向比较：各次采集的选帖数或每帖上限不同，
  数量差异首先反映的是采集参数差异。
```

这正是设计意图：**能比占比，不能比绝对量**，而且原因写在同一页上。
如果只输出那张表，读的人第一眼看到"60 > 50"就会说"延迟退休更热"——那是错的。

### 发现并修掉的一个真 bug

写这段时发现：**清洗档位要到清洗时才确定，而采集参数只在采集时写一次**。
结果所有老会话在对比里都显示"清洗档位未记录"，可比性判断永远退化为"不可比"。

修法两条：
1. `Store.merge_run_params()` + `pipeline.clean()` 里回写
   `clean_tier` / `dedupe_scope` / `use_ai` / `filter_bots` / `pipeline_version`；
2. `build_profiles()` 在参数缺失时**从 `clean_comments.clean_tier` 读回**
   ——这不是猜测，是读自己已经存下来的记录。

这属于"参数留痕"这类容易被忽略、但直接决定功能可用性的工程细节。

### 也顺手记下"同话题重复采集"

同一话题采了多次时给出告警：那适合比较「采集稳定性」，不是跨话题对比。
并且默认排序改成：**有 2 个以上不同话题时，不掺同话题的重复采集**——
否则"跨话题对比"会被悄悄变形成"同话题稳定性检查"。

全量 259 项通过。测试重点不是"能算出来"，而是**克制**：
