# 016 · 采集口径、清洗影响图、话题推荐界面化

日期：2026-10-26　状态：已实施　测试：`tests/test_collection_summary.py`、`tests/test_search_mode.py`、`tests/test_console.py`、`tests/test_stage4.py`

本轮按「先把方法链补齐，再补交互」的顺序做了六件事，全部围绕同一句话：
**报告里写不出"样本怎么来的"，前面采得再多也不像研究。**

## 1. 清洗影响图（需求 B2 的"图"）

之前只有分位数表。表和图的区别不是美观，而是**能不能看出形状**：
如果被删掉的主要是短文本或低粉丝账号，均值可能只动一点，但分布形状会变形。
表看不出来，图一眼能看出来。

`charts.cleaning_comparison(raw_rows, kept_rows, path)` 画两格：
评论长度（density，两次样本量不同所以不能用计数）与粉丝数（log10）。
缺一侧数据就安静返回 `None`，不让"锦上添花"的图拖垮分析。

报告第一节直接引用，并附一句读法：
*看这张图只问一件事——前后两条分布是不是同一个形状。*

## 2. 报告新增「采集口径与样本边界」

不编号，放在正文之前：它是方法前提，不是第零步分析。

内容由 `analyze/collection.py` 合成，来源三处：
采集参数（`params_json`）、实际数据（`created_at`）、研究日志（`comments_done`）。

**最关键的取舍：覆盖度由数据反算，不照抄计划值。**
界面上填了 9-01～9-30，程序可能在 9-20 就停了；照抄计划等于给自己发假通行证。
所以报告写的是"实际覆盖 2026-09-02 ～ 2026-09-20"。

排序生效与否看研究日志里每篇帖子的 `sort_applied`：
只要有一篇为 `False`，就说明"按时间排序"在这批数据里没真正生效。
一个细节：排序本来选的就是热度时，后端没有排序参数**不算失效**，
不能对着一件正常的事打警告符号。

## 3. 话题推荐进界面（需求 E2 收口）

新增面板：描述 → 助手提候选（只给名字与理由）→ 每个候选**真搜一次**量级 →
「用选中话题检索」「查看样例帖子」。

硬约束照旧：**禁止模型虚构讨论量**。量级一律来自 `probe_tag()` 的真实检索，
描述里写明"首 N 页共 M 条"，不冒充话题总量。
「查看样例帖子」优先用探测时留下的真实摘要；没有就现场再查一次，
而不是拿模型的话搪塞。

## 4. 逐帖目标数与二级评论目标数

- CLI `--per-post 1=200,3=50`：编号对应预览列表，映射成 `mid` 后才进采集参数；
  非法写法（`1-200`、`1=0`、`0=5`、`x=5`）逐条给人话提示。
- 二级评论目标数从硬编码 10 变成 `CollectOptions.subcomment_target`，
  界面加了输入框，`--subcomment-target` 也可设；并验证它**真的传到了采集层**。

## 5. 检索口径：话题聚合 vs 关键词全文

`search_query(raw, mode)`：`topic` → `q=#话题#`；`keyword` → `q=关键词`。

这不是文字游戏：话题聚合的样本是"主动参与该话题的人"，
关键词检索里混着"顺口提一句"的帖子。混为一谈，
报告里"该话题参与者如何如何"这句话就不成立。

界面加了单选，CLI 加了 `--search-mode`，口径进参数、进报告、进 `method_note`。

## 6. 修掉一个全局性 bug（console.fail）

`console.fail()` 原本写成 `Console.print(..., file=sys.stderr)`，
而 rich 的 `Console.print` **没有** `file` 参数。后果是：
**所有**命令行失败路径都会抛 `TypeError`，把"你填错了"变成 Python traceback。

这是本轮最值得修的一处，因为它是"错误处理"本身的错误：
用户已经犯错时，工具必须给可读的话，而不是再炸一次。
现在用 `Console(stderr=True)`，并加了 `tests/test_console.py` 盯住
"stdout 干净、stderr 有字、不抛异常"。
