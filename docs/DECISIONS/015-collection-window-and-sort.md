# 015 · 采集算法：时间窗、排序与停止条件

日期：2026-10-26　状态：已实施　测试：`tests/test_window.py`（25 项）

## 需求

> 根据微博平台本身的特点特别是话题、搜索、帖子、评论本身的特点来专门量身定做一套采集算法，
> 能够让用户既能在一个时间窗口内采集评论，又能按热度排序或按时间排序。

## 平台事实（先查清，再设计）

| 通道 | 每页 | 排序 | 时间单调 |
| --- | --- | --- | --- |
| 移动端 `comments/hotflow` | ~10 | **忽略** | ❌ 热门流 |
| 网页端 `statuses/buildComments` | ~20 | `flow=0/1` | ✅ 按时间时 |
| 二级评论 `hotFlowChild` | ~10 | — | — |

关键区别是**时间单调**：按时间流里"这条比窗口早"意味着"后面都更早"，
于是可以提前停止；热门流里这条推论不成立。

如果对热门流也用"看到旧的就停"，就会漏掉窗口内的评论，
而研究者会以为自己把窗口采全了——这是本模块要防的头号错误。

## 设计

新增 `wrc/weibo/window.py`，三个对象：

1. `TimeWindow`：闭区间过滤。日粒度（`05-12`）按"日期有交集"判定，
   否则窗口最后一天会被整片漏掉；**时间未知的评论保留并单独计数**，
   因为解析失败的多是最新的"刚刚/今天"，丢掉会让样本系统性偏旧。
2. `plan_comment_collection()`：纯函数，决定「能不能提前停、页数上限多少」，
   并把理由写成可以直接抄进论文的 `notes`。
3. `WindowCoverage`：实际覆盖范围 + `complete` 标志。

`collect_comments()` 新增 `since/until/max_scan_pages`，停止原因扩展：

| stopped_reason | 含义 |
| --- | --- |
| `reached_target` | 窗口内凑够目标条数 |
| `reached_window_start` | 时间单调流已翻过窗口起点 → **窗口完整覆盖** |
| `no_more_from_platform` | 平台翻到底（时间单调时同样视为覆盖完成） |
| `page_cap` | 触及页数上限（热门流：窗口可能没采全） |
| `budget_near_limit` | 剩余预算压低页数 → 提前停，已采数据保留 |

## 三个判断

**一、目标数的语义变了。**
设了窗口后 `target` 指「窗口内凑够多少条」。若沿用"取 N 条再筛窗口"，
窗口越大可用样本越少，而界面还显示"目标 50"——那是假信息。

**二、排序没生效必须写出来。**
移动端后端不认排序参数。工具不假装成功：`sort_applied=false` 进日志、
进参数、进方法卡片，`plan.notes` 里有一句"排序未生效"。

**三、预算不足改为"停"而不是"抛"。**
旧行为：页数上限不受预算约束，翻到预算耗尽时 `BudgetExceeded` 抛出，
`pipeline` 捕获后跳过整篇帖子——那一篇已采到的评论全部不落库。
这看起来"暴露了问题"，实际后果更糟。现在预算压低页数上限，停止原因记
`budget_near_limit`，已采数据照常返回。
（原测试 `test_budget_exhaustion_propagates_...` 相应改写为
`test_budget_pressure_stops_with_partial_data_instead_of_raising`。）

## 界面

- **复选框**：帖子列表新增「选」列，点方框或按空格切换；只有勾选的会被采集。
  「全选 / 全不选 / 反选」「已勾选 N/M 篇」实时显示。
  勾选状态按 `mid` 存而不是行号，重新检索不会串行。
  为什么不用一行行 `Checkbutton`：几百条候选时会明显卡顿，
  而 Treeview 的点选列在行为上等价。
- **时间窗**：起止两个输入框 + 「近 7 天 / 近 30 天 / 不限」快捷按钮。
  只填日期时，起点取 00:00、终点取 23:59（这两条写在输入框下方）。
  格式错误当场拦下，不静默当成"不限"。
- **评论排序**：热度优先 / 时间优先，并直接标注"仅网页端生效"。

## 顺带修的两处

1. `_FULL_DATE_TIME_RE` 只认到分钟，`2026-09-20 10:00:00` 解析成"未知时间"，
   于是所有带秒的时间都变成 `created_at=None`——窗口过滤会因此全部放行。
   现在允许可选秒，也接受 `T` 分隔符。
2. 时间窗是朴素 datetime，而评论时间是带时区的 CST；
   直接比较会抛 `TypeError: can't compare offset-naive and offset-aware`。
   现在统一剥时区再比（全项目都是北京时间，不会引入歧义）。

## 已知限制

- 热门流下窗口覆盖率**无法保证**，这是平台限制，不是实现偷懒；
  要保证覆盖请用 `--comment-sort time` 配网页端后端。
- `max_scan_pages` 缺省按目标数 5 倍给余量；窗口极大时仍需提高
  请求上限或在界面上调低目标。
- 帖子层面的"按热度/按时间"仍是**本地重排**，不是平台排序；
  界面与报告都如实标注，不冒充平台行为。
