# 决策记录 010 · 研究日志正式版（可复现性附录）

- 阶段：P2 收尾（最后一项）
- 状态：已实现，且在两个真实会话上验证通过

需求里这一项写的是"研究日志正式版"。落到论文里，它其实就是**一份附录**：
审稿人或导师想复核你的分析，必须能在一个地方查到
「数据从哪来、怎么清洗、用什么模型、参数是什么、结果文件是哪一份、能复现到什么程度」。

---

## 1. 为什么不能只把 JSONL 渲染成 Markdown

P1 起就有的 `research_log.py` 记的是**事件流**：几点几分发了第几次请求、
清洗移除了几条。它是**过程留痕**，回答"当时发生了什么"。

但论文附录要回答的是另一组问题：环境是什么、参数是什么、文件是哪一份、
**以及哪些结论可以复现、哪些不能**。事件流里没有这些，也无法从中推导。

所以拆成两个东西，都保留：

| | `research_log.py` | `reproducibility.py`（本项） |
| --- | --- | --- |
| 内容 | 事件流（JSONL + 可读草稿） | 结构化附录（环境/参数/指纹/等级） |
| 用途 | 自己回看、排查、复述 | 直接进论文附录 |
| 读者 | 研究者本人 | 审稿人、导师、复核者 |

## 2. 最重要的一节：可复现性分级

这是整份附录里唯一"我替你做了判断"的地方，所以单独说明。

不能笼统地写"本流程可复现"——那是这类工具最常见的不诚实。附录逐环节给等级：

| 环节 | 等级 | 依据 |
| --- | --- | --- |
| 数据采集 | 可用相同参数近似重采 | 平台内容随时间变化，同参数重采得到的是**不同**样本 |
| 清洗 | 可逐位复现 | 固定规则表 + 固定顺序 + 固定种子 |
| 情感标注（LLM 通道） | **不可复现** | 服务端模型版本与采样随机性都不在你手里 |
| 情感标注（本地模型） | 可逐位复现 | ONNX 前向推理确定性；前提是权重文件字节一致 |
| 话语聚类 | 可逐位复现 | K-Means 固定 `random_state`；**依赖句向量模型文件一致** |
| 用户社群聚类 | 可逐位复现 | 特征计算确定 + 固定种子 |
| 时间演变 / 回复结构 / 交叉表 | 可逐位复现 | 纯计数与重排，无随机性 |
| 报告与图表 | 可逐位复现 | 只排版，不引入新计算 |

三处刻意写得很具体：

1. **LLM 通道写"不可复现"而不是"部分可复现"**。说得含糊，作者就敢在论文里
   写"结果可复现"，而实际复核时标签对不上。
2. **聚类的"可复现"附带前提**：模型文件必须字节一致。所以第七节列出
   ONNX 权重的 SHA-256（`bge-small-zh-v1.5` = `15b717c3…`，
   `distilbert-sentiment-zh` = `9570fdd7…`）。只说"用了 bge-small-zh"是不够的，
   量化版与全精度版会给出不同向量，簇的划分也会不同。
3. **采集写"近似重采"**：任何声称"这次采集可复现"的说法都是错的，
   微博的内容每天都在变。

## 3. 把"可复现"从声明变成可验证的检查

既然表里写了"清洗：可逐位复现"，就应该能被验证。所以加了：

```bash
python -m wrc.cli reclean --run <会话ID>
```

它用**当前代码**对同一份原始数据重跑清洗，与库中 `clean_comments` 逐条比对
`kept` 与 `drop_reasons`，输出：

```
- 逐条比对：50 条，一致 50 条，不一致 0 条
结论：**重放结果与库中记录完全一致**。这条链路上的「可逐位复现」是可验证的，不是声明。
```

并且**刻意不提供写入模式**。一旦可以覆盖，"重放"就会变成"让数据看起来和上次一致"，
那正好破坏可复现性。

### 这个功能立刻抓出了两个真问题

**问题一**：小米会话第一次重放时 46/50 一致，4 条不一致，差异全是
`drop_suspected_bots:粉丝N`。原因：僵尸号过滤是"可选步骤"，
当时界面上开启了，但**没有记进采集参数**，重放按默认关闭、于是少删了 4 条。

修法：
1. `pipeline.clean()` 现在会把 `filter_bots` / `dedupe_scope` / `use_ai` /
   `clean_tier` / `pipeline_version` 一起回写进 `collection_runs.params_json`；
2. 对历史会话，`verify_clean_replay` 从 `drop_reasons` 里**反推**当时开没开
   ——库里有 `drop_suspected_bots` 就证明开过。这是读自己的执行痕迹，
   不是猜，并且会在输出与附录里标注「依据库中 drop_reasons 推定」。

**问题二**：附录原本把自己的 `appendix.md` 也算进校验和表里。
但附录是先算哈希再写入文件，写完之后哈希必然对不上——
一个一眼看不出、但确实是假的数字。现在 `collect_files()` 明确排除
`appendix.*`，文档里也写明了原因。

## 4. 附录的其余各节

- **一、运行环境**：Python / 操作系统 / 架构 / 10 个关键依赖的实际版本，
  没装的写"未安装"。
  **刻意不写本机路径**——附录会流出到论文和公开材料，不该带目录结构。
- **二、采集**：模式（mock 会打上"非真实数据"标记）、排序、全部参数、
  以及"热门评论流偏袒高互动"这条约束。
- **三、清洗**：档位、管线版本、输入/保留/保留率、**按 `drop_reasons` 统计的移除明细**。
  标签保留冒号后的细节（`广告关键词（加V私信）`），因为研究者要判断规则有没有误杀。
- **四、分析模块**：每个模块的 analysis_id、运行时间、全部方法参数。
- **五、大模型调用**：服务地址、模型、调用次数、token 用量，
  并注明"未记录的生成参数说明当时未显式设置，服务端默认值不受控制"。
- **六、复现等级** + 本次重放校验结论。
- **七、模型文件指纹**。
- **八、产出文件与校验和**（证明"论文里引用的数据就是这一份"）。
- **九、复核步骤**：给第三方的 5 步清单，每条都是可执行的命令。
- **十、已知局限**：热门评论流偏差、时间精度、无人工双编码、附录不等于研究设计。

## 5. 接入方式

```bash
python -m wrc.cli appendix              # 生成最近一次会话的附录
python -m wrc.cli appendix --all        # 所有会话各一份
python -m wrc.cli appendix --no-hash    # 跳过模型指纹（快）
python -m wrc.cli reclean               # 清洗重放校验（只读）
```

- `run` 全流程结束后自动生成 `appendix.md`（界面与命令行都走这条路）。
- 产物：`data/exports/<会话ID>/appendix.md` + `appendix.docx`（Word 直接贴进附录）。

**为什么允许随时重跑**：附录里的 SHA-256 会随文件变化。数据重新导出过、
报告重新生成过，就应该重跑一次附录，否则校验和对不上。

## 6. 测试

新增 17 项（`tests/test_reproducibility.py`），全量 276 项通过。重点：

| 断言 | 防的是什么 |
| --- | --- |
| 十个小节齐全、缺项写"未记录" | 附录半途而废或有空字段 |

| 聚类的复现前提含 SHA-256 | 只说模型名、不提文件版本 |

| 重放能发现人为篡改 | 校验只是摆设 |
| `ai_*` 原因 → 拒绝重放并说明 | 假装规则能重放模型判定 |
| 从 `drop_reasons` 推断 bot 过滤并标注"推定" | 悄悄假设配置、不告知 |
