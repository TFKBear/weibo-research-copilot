### 1.1 已完成的实测（未登录基线）

在没有任何登录态的前提下，把"能验证的部分"先验证掉了，

| `m.weibo.cn/api/config` | 200，`login:false`，下发访客 Cookie | **传输链路成立**，主链路方案（APIRequestContext + 自定义 Header）可用 |

对一个要求可复现的研究工具来说，虚假的冗余比没有冗余更危险。

## 2. 为什么这么做

### 2.1 先打最不确定的一环
需求文档判断正确：登录态时效短、反爬强，是整个产品的最大技术不确定性。
因此第 1 步没有写任何 UI、没有写分析模块，而是把「浏览器登录态能否复用」
做成一条可重复执行的脚本。

### 2.2 把猜测降级为可执行的探测
开发时有 10 条假设无法在无网络登录的情况下确认（见 ARCHITECTURE §8）。
处理方式是**不猜**：
- 代码注释里标「待验证」；
- 用户可见文案里写清「本地重排，不等于平台排序」；
- 每一条都做成了 `03_probe.py` 的一个探测项，跑一次就能得到结论。

这条路比"先按猜测写，出问题再说"慢，但它是唯一能让研究者在论文里
诚实交代方法的做法。

### 2.3 在 P0 里提前把匿名化做完整
需求把「伦理与匿名化」列为 P0 且要求与清洗同步交付，这是对的。
本步实现的不只是"删字段"，而是：
导出字段白名单 + HMAC 稳定伪 ID（保留用户级分析能力）+ 省级聚合 + k-匿名抑制原语 + 强制使用声明 + 校验和。

其中「匿名化放在导出而非入库」是一个关键判断：入库即脱敏会让 P1 的用户级聚类
彻底失去可行性，而这个损失要到第 3 步才会暴露——那时已经太晚。

### 2.4 清洗先做「轻度档」，但把结构做对
第 1 步只实现模块 B1 的轻度档，但清洗被设计成**步骤表**而不是单一函数：
每步可命名、可计数、可关闭、被移除样本可按 cid 恢复。
中度/重度档（广告规则表、僵尸号、BERT 分类、协同相似度）按节奏留到第 2 步，
届时只需往 `STEPS` 追加，不需要重构。

### 2.5 顺手解决的两个「学生会第一眼卡住」的问题
- **Windows 中文乱码**：Python 在 Windows 上默认用 ANSI 代码页，中文提示直接抛
  `UnicodeEncodeError`。已在 `console.py` 统一转 UTF-8。这个问题不解决，工具在
  目标用户的主力环境上等于不可用。
- **浏览器未安装**：Playwright 的原始报错是一大段路径与版本号。已转译为
  「执行 `python -m playwright install chromium`」的三步指引。

## 3. 遇到的不确定性

### 3.1 已解决
| 问题 | 处理 |
| --- | --- |
| `max_id` 可能原地不动导致无限翻页 | 加 cursor 停滞检测，停止并把 `cursor_stalled` 记入日志；有专门测试 |
| 用户级分析需要稳定用户标识，但与匿名化冲突 | 采用 HMAC(本地盐, user_id) 伪 ID，分析可用、导出不可反查 |
| 微博时间混用相对/绝对/仅到日 | 保留原文 + 精度标签，不伪造 `00:00:00` |
| 接口波动时无法区分"平台变了"还是"代码坏了" | 引入 `MockFetcher` + 确定性场景，管线可离线回归 |
| 需求未明确「按热度」到底是平台排序还是本地排序 | 一律标注为本地重排，并在探测脚本里验证平台参数是否可用 |
| 联网基础可行性 | 已实测：m 站接口可达、鉴权边界明确（见 §1.1） |
| Playwright 浏览器下载卡死 | 已实现系统 Chrome / Edge 自动回退并实测通过 |
| 桌面检索能否当降级通道 | 已实测不能，代码与文档已同步收敛 |

### 3.2 未解决（需要实机）
1. **登录态能否稳定复用**——最大风险项。若扫码登录后 `storage_state` 在几小时内失效，
   P0 的整个交互设计需要重新考虑（可能要引导用户在采集期间保持浏览器开着）。
2. **评论接口的真实形态**——未登录时检索就被挡住，评论接口连探测都做不了。
   它的字段名（`like_counts` vs `like_count`、`total_number`）与 pagination 行为都需要登录后确认。
3. **432 / 418 的实际阈值**——默认 1.5–3s 延迟 + 120 次上限是保守估计，
   真实环境下可能仍需下调。
4. **检索排序参数**——直接影响「按热度」能否做成真实平台排序，还是只能本地重排。

### 3.3 明确的判断分歧点
需求文档的「轻度档」包含"去重（精确重复）"。我实现了它，但需要提醒：

> 微博评论区里完全相同的短评论（如"同意""支持"）有时是**真实的集体表达**，
> 不一定是水军。全局去重会系统性地削弱这类声音。

因此实现上默认 `dedupe_scope="post"`（仅帖内去重，风险最低），
全局去重需要用户显式开启，且清洗报告会给出移除量与被移除样本以供判断。
**这是一个规范性选择，最终应由研究者而非工具决定**——如果产品负责人认为
轻度档就不该做去重，改动只需一行配置。

## 4. 需要人类确认的事项

### 需要立刻确认（影响第 2 步工作量）

1. **实机跑一次登录**：`python spikes/01_login.py`，然后 `python spikes/01_login.py --check`。
   结果决定是否需要调整整个登录交互设计。这是目前唯一的硬阻塞项。
2. **登录后重跑探测**：`python spikes/03_probe.py --tag <你关心的真实话题>`。
   未登录基线已完成（见 §1.1），剩下 6 条假设要靠这一步确定，
   其中最关键的是「按热度能不能做成平台真实排序」。
3. **真实采集 50 条**：`python spikes/02_chain.py --tag <话题> --select 1 --comments 50 --consent`。
   重点看：延迟是否触发 432、评论能否翻到第 2 页之后、导出的 CSV 用 Excel 打开是否正常。

### 需要产品负责人决策

4. **轻度档是否保留「精确去重」**（见 §3.3）。当前默认帖内去重。
5. **二级评论的默认值**——当前默认关闭。若目标课题（如"楼中楼中的反驳结构"）需要，
   应改成按帖询问，而不是全局开关。
6. **第 2 步范围确认**：中度/重度清洗档涉及规则表与 BERT 分类模型（需下载模型、
   首次约 400MB、CPU 推理较慢）。是否在第 2 步就引入 BERT，还是先把中度档做完再看？
   我的建议是**先做中度档**（规则表 + 僵尸号判定，零模型依赖），把 BERT 推到 P1
   与情感分析一起做，这样只需要维护一次模型加载与版本记录。
7. **是否接受"请求硬上限 120"**——这个数字决定了单次能采多少。
   按每帖 50 条评论、每页 20 条估算，120 次请求约可覆盖 2–3 篇帖子。
   若目标课题需要 10 篇帖子 × 500 条评论，需要重新设计预算模型（例如按任务分批 + 冷却）。

### 不需要确认、但请知悉

8. 本步按「P0 未完成前不得启动 P1」执行，未编写任何情感分析、聚类、AI 助手代码，
   也未编写前端。`pyproject.toml` 里预留了 `[ml]` 可选依赖组，未安装。
9. 真实采集前请确认所在机构的伦理审查要求；工具已内嵌匿名化与使用声明，
