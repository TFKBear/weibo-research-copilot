## 1. E1 方法助手

### 需求边界与实现对应

需求把助手的角色限定为"方法顾问 + 操作向导"，并明确"不替代用户做分析决策"。
实现上拆成两个**互不依赖**的入口，这是刻意的：

| 入口 | 实现方式 | 为什么 |
| --- | --- | --- |
| `ask()` 自然语言问答 | 走 LLM，注入当前会话上下文 | 解释概念需要语言能力 |
| `suggest_next_steps()` 下一步建议 | **纯规则**，不走 LLM | 下一步该干什么由数据状态唯一决定，用规则算出来的建议确定、可复现 |

**为什么建议不用 LLM**：同一个数据状态应该永远给出同一个建议。
如果建议随模型温度变化，用户会困惑，研究者也无法复现"当时工具提示了什么"。
LLM 负责解释，规则负责指路。

### 上下文注入

助手能看到（并会写进提示词）：
话题、候选帖数、评论数、清洗档位与保留率、情感分布与不一致率、
两个聚类的 K 与轮廓系数、参与用户数、当前 LLM 模型、本地模型是否就绪。

这段上下文同时是可审计的——研究者能看到"助手当时依据的是什么数据"。

### 实测

真实提问"我的样本量够做聚类吗"，助手回答里正确指出：
- 话语聚类轮廓系数 0.1233，K=4"更像被算法强行切开"，不宜写进结论；
- 用户社群轮廓系数 0.64 看起来不错，但**它主动指出上下文里缺用户数**，
  认为无法判断是否虚高；
- 样本只来自 1 篇帖子，不能外推到话题层面。

第三点尤其值得记：它抓住了"同质性强"这个我没写进上下文的隐含问题。
它后来发现的"缺用户数"也确实是我上下文的一个遗漏，已补上。

## 2. P2 话题推荐

### 需求里最硬的一条约束

> 严禁 LLM 在未做实际探测的情况下虚构 tag 的讨论量。

实现方式：**LLM 只负责想标签名和理由，量级一律由真实请求提供**。
提示词里明确写了"绝对不要估计讨论量"。

### 量级口径必须诚实

微博检索接口**不返回话题总帖数**（`cardlistInfo.total` 在移动端检索里通常缺失）。
所以报告的是**活跃度信号**：

- 首 2 页能拿到多少条**不同**帖子
- 互动量中位数
- 最新一条的日期
- 2 条样例帖

输出里明确写着："这是首若干页能拿到的帖子数与互动水平，用来判断标签是否活跃，
**不等于话题总量**。"

把探测值说成总量，就是另一种形式的虚构——和让模型编数字一样有害。

### 实测

```
1. 小米SU7        讨论活跃（首 2 页共 20 条），互动中位数 681，最新一条 2026-10-25
2. 小米汽车       讨论活跃（首 2 页共 20 条），互动中位数 95，最新一条 2026-10-25
3. 小米SU7事故    讨论活跃（首 2 页共 20 条），互动中位数 30，最新一条 2026-10-21
```

三个标签都真实存在且活跃。按实测活跃度排序，把"检索不到"的候选排到最后，
避免推荐一堆死标签。

**注意一个细节**：三个标签都是"讨论活跃（20 条）"——因为首 2 页最多就是 20 条。
这说明**该指标有天花板**，无法区分"刚好有 20 条"和"有 20 万条"。
目前靠互动中位数（681 / 95 / 30）来区分热度。这个局限应该写进方法说明。

## 3. 新增命令

```bash
python -m wrc.cli ask --suggest             # 规则建议，不花钱
python -m wrc.cli ask "我的样本量够聚类吗"   # 结合上下文问答
python -m wrc.cli tags "事件描述" --limit 5  # 候选话题 + 真实探测
python -m wrc.cli analyze --limit 200       # 分析（转发到 tools/run_analysis.py）
python -m wrc.cli report                    # 从数据库重建报告
```

界面上：分析区新增「问方法助手」输入框 +「下一步建议」按钮。

## 4. 测试

新增 15 项（助手 10 项 + 话题推荐 9 项，合计 199 项全通过）。

重点覆盖：
- 建议的**确定性**（同一状态永远同一建议）
- 建议里的数字必须来自上下文，不能是套话
- 模型即使自作主张返回 `volume: 99999`，解析层也不把它当量级
- 渲染时必须带"不等于话题总量"的说明
