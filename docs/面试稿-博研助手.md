## 一、开场：2 分钟版

我做的是一个**面向社科类本科生与研究生的微博舆论研究工具**，叫「博研助手」。

起因很具体：社科学生做微博研究，实际卡点不在"分析"，而在三件事——
数据采不下来、清洗过程是黑箱、结论在论文里交代不清。市面上的商业舆情工具都是奔着
"监测报表"去的：一键出词云、情感饼图，但你问它"这 3000 条是怎么筛出来的、
被删掉的 200 条长什么样、模型版本是什么"，它答不出来。

所以我给产品定了三条不可妥协的原则：**可追溯优先于自动化、可解释清洗优先于极限去噪、
伦理合规内嵌而不是事后补丁**。整个产品就是围绕这三条做的取舍。

结果上，它能做到：输入一个话题和时间窗，自动完成采集 → 清洗 → 情感/立场/聚类分析 →
图表与报告，输出的是**能直接贴进论文方法段**的东西——逐条数据、清洗影响图、
方法卡片、可复现性附录、研究日志。真实跑测里，404 条原始评论保留 375 条（92.8%），
一次产出 12 张图 + Word 报告 + 附录，全部通过交付物自检。

如果一句话概括我在这个项目里的角色：**我是定义"什么该由机器做、什么必须交回给人"的人**，
并且把这个判断落成了可验收的指标和可运行的代码。

## 二、用户与问题（我为什么做这个）

**目标用户**：社科类本科/研究生的课程论文、毕业论文、课题数据收集。

**三个真实痛点**（来自与目标用户的实际操作反馈）：

| 痛点 | 具体表现 | 后果 |
| --- | --- | --- |
| 采集门槛高 | 登录态、翻页游标、风控、评论接口结构变更 | 大部分学生写脚本卡在这一步就放弃 |
| 清洗是黑箱 | 商业工具"一键清洗"，不说删了什么 | 论文里无法交代抽样过程，被质疑就答不上来 |
| 伦理不可见 | 导出带用户 ID、昵称、地区 | 数据不能用于正式研究，甚至有合规风险 |

**我的产品判断**：这个场景的价值不在"更聪明的模型"，而在**更可信的证据链**。
因为用户最终要交的不是一份报表，是一篇要被人审的论文。

## 三、我怎么定义产品（分层与范围控制）

按"是否服务于可复现的社科研究"重排需求优先级，并明确 P0 未完成不启动 P1：

| 层级 | 内容 | 判断依据 |
| --- | --- | --- |
| P0 | 登录态复用、话题检索、可解释清洗、匿名化导出 | 没有可采数据与合规出口，产品不成立 |
| P1 | 评论采集（规模/时间窗/排序可配）、情感分析、聚类与社群、AI 方法助手 | 研究的主路径 |
| P2 | 话题推荐、报告导出、研究日志 | 研究闭环 |
| P3 | 事件研究、跨话题对比、二级评论结构 | 深度增强 |

一个关键的**否定式决策**：我拒绝了很多"看起来智能"的功能——
不做自动下结论、不做"一键生成论文结论"、不用评论量最大的那天冒充"事件日"。
因为这类功能会直接毁掉研究可信度，而这正是产品的立身之本。

## 四、三个关键难点与解法（STAR 主故事）

### 故事 1：采集——平台不给你"按时间"，你要自己定义"什么时候停"

**S**：用户要"某个时间窗内的评论"。直觉做法是翻页翻到时间窗起点就停。

**T**：但微博评论区有两套接口：移动端热门流（时间**不单调**）、网页端按时间流（单调）。

**A**：
- 我把"停止条件"抽象成独立模块 `window.py`：只有时间单调的流才允许
  "越过窗口起点即停"，并宣称窗口已完整覆盖；热门流**禁止**这样停，
  只能按条数/预算停止，并如实报告"窗口未完整覆盖"。
- 时间窗过滤不丢"时间未知"的评论——它们往往是最新的，丢了会让样本偏旧。
- 目标条数的语义改成"**窗口内**要凑够多少条"，而不是"先取 N 条再筛窗口"
  （后者会让窗口越大、可用样本越少，而界面还显示"目标 100 条"）。
- 覆盖度**由数据反算**，不照抄计划值：真实跑测里用户设了 2026-01-01 起的窗口，
  实际只覆盖到 2026-08-16，报告写的是后者。

**结果**：采集这个模块从"能跑"变成"能被审"——每一次为什么停下来都有名字：
`reached_target / reached_window_start / page_cap / budget_near_limit`。

### 故事 2：模型质量——用人工复核把情感标注从 20% 错误压到 5%

**S**：情感分析用 LLM + 本地模型双通道。第一版提示词在 20 条人工复核里错 4 条（20%）。

**T**：错因必须能归因，否则改提示词就是碰运气。

**A**：
- 建了**信度抽样机制**：随机抽 min(200, 总量×5%) 条跑双通道，不一致率 >15% 告警。
  首轮双通道不一致率 30%。
- 逐条看人工复核表，把错因归档成两类：
  ① **没有情绪词的抱怨**被判中性（"很多老年人没退休金的"）；
  ② **诉苦但落点是认同**被判负面（"我们这代人不容易……还是感谢国家"）。
- 不是继续加抽象规则，而是**把 5 条真实错例直接写进 few-shot**，
  同时加两条判据（"看这句话在指出谁的损失"、"找句子落点有没有认同表态"），
  并给反例防止矫枉过正（"我今年30岁"仍是中性）。

**结果**：同一批 20 条，错误率 **20% → 5%**；双通道不一致率 **30% → 20%**。
提示词版本号从 v1.1.0 升到 v1.2.0，旧结论与新版本可区分——这也是"可追溯"的一部分。

### 故事 3：可信——把"可复现"做成产品功能，而不是文档承诺

**S**：学生写论文最怕被问"你的数据怎么来的"。

**T**：如果工具只能给结果、不能给证据链，用户还是要手写方法段。

**A**：做成四件套：
- **方法卡片**（每个分析模块一张）：模型、提示词版本、超参、抽样率、清洗档位、时间戳；
- **可复现性附录**：分环节复现等级、模型文件 SHA-256、清洗重放校验；
- **研究日志**：逐事件记录（133 条事件 / 一次采集）；
- **交付物自检**：一条命令检查 11 个必需文件、隐私字段、报告结构、口径一致性。

**结果**：真实跑测里，附录和报告对"检索口径/时间窗/实际覆盖"的表述**逐字一致**
（这是被测试盯住的不变量）；任何一次导出都能用一条命令证明"齐了、对得上、没泄露"。

## 五、真实迭代：用户的六条反馈与我的处理

这是我认为最能体现产品经理价值的部分——**两次真实跑测之后的六条反馈，我一周内全部落地**：

| 用户反馈 | 我的处理 | 产品判断 |
| --- | --- | --- |
| 打开后按钮被折叠，要手动拉大窗口 | 按屏幕 94%×90% 开窗 + Windows 最大化 + 滚轮绑定 | 这不是美观问题，是"首屏可用性"，属于 P0 |
| 只能采 20 篇帖子、每帖 50 条，样本太小 | 候选 20–500（默认 100）、每帖 10–2000（默认 100）、请求上限 20–3000，并**实时估算"期望样本 vs 请求数"** | 关键不是调大数字，是让"样本量与预算的冲突"在开跑前暴露 |
| 默认话题是示例词，以为已选好 | 默认留空 | 默认值会被当成决策 |
| 助手应该懂这个软件才能指引操作 | 把五区操作手册 + 五个常见坑注入 system prompt | AI 助手不是通用客服，要"懂产品" |
| 图表太简单 | 引入 seaborn 统一视觉、dpi 提到 200、图表扩到 14 种可选 | 论文插图要求"能直接放进 Word"，不是能看就行 |
| 报告缺了第九节 | 第九节永远存在，没做事件研究也说明原因与补做方法 | 结构稳定才能被逐节核对 |

这套迭代节奏来自一个习惯：**每次真实跑测后，把问题写进决策记录（23 份），
能自动检查的写成测试，不能的写成待办**。目前自动化测试 400 余项，
一次 `tools/check.py` 全绿才算"可交付"。

## 七、复盘：我做得不够好的地方（面试官很爱问）

1. **可用性验证滞后**。我做了界面自检（控件能建、勾选逻辑对），
   但"没读说明书的人会不会卡在第 3 步"必须真人测。这已经列入下一步，
   也是我判断"能不能真正落地"的最后一个门槛。
2. **聚类结论不够硬**。轮廓系数 0.1363，簇边界不清晰。
   我的处理是**让工具自己告警**（低于 0.25 提示"不宜作为分类结论"），
   而不是硬写进报告——宁可少一个亮点，也不要一个站不住的结论。
3. **立场标注是单通道**。受成本限制没做双编码员，只在方法卡片里如实披露。
   这是产品取舍，但在学术场景里仍是风险点，下一版会加第二编码员抽样。

## 八、与中移互联网 AI 产品经理岗位的匹配

| 岗位需要的能力 | 我在这个项目里的对应证据 |
| --- | --- |
| 用户洞察与场景定义 | 从"学生论文答辩被问数据来源"倒推产品原则，而不是从技术能力出发 |
| 需求分层与范围控制 | P0–P3 分级，明确"P0 未完成不启动 P1"，拒绝多个"看起来智能"的功能 |
| 模型选型与评测 | 双通道对照 + 抽样信度 + 人工复核闭环，用错误率而不是"感觉准"来验收 |
| 工程协同 | 与开发同一套决策记录与验收命令；把口径做成单一来源，四处渲染逐字一致 |
| 合规与伦理 | 匿名化（HMAC 伪 ID、省级聚合）、k-匿名（n<5 抑制）、导出前声明确认 |
| 平台化思维 | 采集口径（话题/关键词）、停止条件、图表选择都做成可配置项，换平台只需替换采集层 |

**为什么是中移互联网**：这个项目让我确认自己擅长的是"**把 AI 能力变成可信赖的生产力工具**"——
不是做 demo，而是解决"用户敢不敢把它写进正式材料"的问题。
中移互联网做的是面向大量真实用户的 AI 产品，**可信、可解释、可运维**比"炫技"更重要，
这正是我在这个项目里反复练的那件事。

## 九、常见追问与回答要点

**Q：为什么用 Tkinter 而不是 Web？**
A：目标用户是一次性完成一次研究的个人研究者，不是团队协作；
本地跑、无需部署、数据不出本机，反而更符合伦理要求。
代价是界面表现力有限——所以我用"分区 + 一键完成"降低学习成本，
而不是堆视觉。如果要做多用户协作版本，我会换成 Web + 服务端采集。

**Q：LLM 在这里到底解决了什么？**
A：三件事：情感标注、立场标注、方法问答。前两个的价值是**把人工编码的成本降到可承受**，
但我没有让 LLM 代替研究者——所以设计了双通道对照、信度抽样、人工复核入口。
第三个是"降低工具学习门槛"，但要求它懂这个软件，否则就是通用客服。

**Q：怎么保证模型输出可信？**
A：三层：① 双通道交叉 + 不一致率告警；② 人工复核样本（20 条一轮，错误率作为验收指标）；
③ 方法卡片如实写模型、提示词版本与局限。**不承诺"准确"，承诺"可核查"**。

**Q：如果只能保留一个功能，你留哪个？**
A：可复现性附录。因为它决定了这份数据能不能被用于正式研究——
没有它，前面采得再多也只是"一份不知道哪来的 CSV"。

**Q：这个产品的商业化可能？**
A：面向个人研究者是工具订阅（低客单价、高口碑）；
更有价值的是**高校/研究机构的方法学教学场景**——它天然带"清洗影响图、信度抽样、
方法卡片"这些教学素材。但商业化不是我这个阶段的目标，先把"可信"做扎实。
